# oci-freetier-creator

> Part of a multi-image repo - see the [root README](../README.md) for how
> the generic per-folder build workflow works. Everything below is scoped
> to this folder; run these commands from inside it
> (`cd oci-freetier-creator` first if you're at the repo root).

Runs [mohankumarpaluru/oracle-freetier-instance-creation](https://github.com/mohankumarpaluru/oracle-freetier-instance-creation)'s
`main.py` unattended in a container: it polls the OCI API on a timer until
it can successfully create an Oracle Cloud **Always Free** compute instance
(free-tier ARM/AMD capacity is frequently exhausted, so this is normally
left running for hours/days until a slot opens up).

Configured entirely through environment variables - no interactive
`setup_env.sh`, no manually-created `oci_config`/`oci_api_private_key.pem`
files to mount. `entrypoint.sh` generates both from env vars at container
start (see `.env.example`).

## Quick start with docker compose

Two compose files, depending on whether you want to build from this repo's
source or just run the already-published image:

- **`docker-compose.yml`** - builds the image locally from the `Dockerfile`
  in this repo.
- **`docker-compose.hub.yml`** - pulls
  [`sudtanj/oci-freetier-creator`](https://hub.docker.com/r/sudtanj/oci-freetier-creator)
  from Docker Hub instead of building.

```bash
cp .env.example .env
# edit .env - at minimum: OCI_USER_OCID, OCI_FINGERPRINT, OCI_TENANCY_OCID,
# OCI_REGION, OCI_PRIVATE_KEY_BASE64, OCT_FREE_AD, OCI_SUBNET_ID

# Build locally:
docker compose up -d

# Or pull the published image instead:
docker compose -f docker-compose.hub.yml up -d

# Watch it work:
docker compose logs -f
```

Where to get each required value: OCI console -> Profile -> My profile ->
API keys -> Add API key (gives you `OCI_USER_OCID`/`OCI_FINGERPRINT`/the
private key); `OCI_TENANCY_OCID` and `OCI_REGION` are shown on the same
page; `OCT_FREE_AD` is your tenancy's eligible Availability Domain
(Governance & Administration -> Tenancy details, or
`oci iam availability-domain list`); `OCI_SUBNET_ID` is an existing subnet
in the VCN/compartment you want the instance in.

`main.py` runs once in the foreground and retries internally (every
`REQUEST_WAIT_TIME_SECS`) until it either creates the instance or hits a
fatal error - it's a normal long-running process here, not a cron job.
Check `docker compose logs` and the `oci-data` volume's `INSTANCE_CREATED`
/ `launch_instance.log` / `ERROR_IN_CONFIG.log` for status.

## Persisted state

Everything main.py generates or writes lives under `/app` inside the
container, persisted in the `oci-data` named volume:

- `.oci/config` + `.oci/oci_api_private_key.pem` - generated from your env
  vars at container start (regenerated from env vars every start, so
  editing `.env` and recreating the container is enough to change them).
- `.oci/id_rsa.pub` (+ its private half) - auto-generated by `main.py` on
  first run if you don't supply your own via `SSH_PUBLIC_KEY`. Persisted
  deliberately: regenerating it after an instance already exists would
  leave you unable to SSH in with the old key.
- `INSTANCE_CREATED`, `launch_instance.log`, `setup_and_info.log`,
  `ERROR_IN_CONFIG.log`, `UNHANDLED_ERROR.log` - `main.py`'s own output,
  same filenames as upstream's non-Docker instructions.

## Notifications

`main.py` itself (not upstream's `setup_init.sh` wrapper, which this image
doesn't use) sends:
- **Discord**, via `DISCORD_WEBHOOK`.
- **Gmail**, via `NOTIFY_EMAIL=True` + `EMAIL` + `EMAIL_PASSWORD` (a Gmail
  [app password](https://myaccount.google.com/apppasswords), not your
  normal account password).

Telegram (`TELEGRAM_TOKEN`/`TELEGRAM_USER_ID`, documented upstream) is only
implemented in `setup_init.sh`'s own bash notification functions, not in
`main.py`, so it has no effect here.

## How it's built

Multi-stage `Dockerfile`, `python:3.12-alpine` base per the request this
was built to:

1. **Builder stage**: clones the upstream repo, creates a venv, and `pip
   install`s its `requirements.txt` (`oci`, `paramiko`, `python-dotenv`,
   `requests`). Alpine has no manylinux wheels for these (musl, not glibc),
   so `paramiko`'s `cryptography` dependency needs to compile its Rust
   extension from source - `gcc`/`musl-dev`/`libffi-dev`/`openssl-dev`/
   `cargo`/`rust` are installed only in this stage.
2. **Final stage**: copies just the built venv and `main.py` +
   `email_content.html` (the only two runtime files actually needed) into
   a fresh `python:3.12-alpine`, with only the runtime shared libs
   (`libffi`, `openssl`) and `su-exec` (alpine's minimal `gosu` equivalent)
   - none of the build toolchain from stage 1.

`entrypoint.sh` runs as root (self-heals `/app`'s ownership on every start,
same defensive pattern as this repo's other images), generates
`oci_config` + the private key file + an SSH public key file from env vars,
then drops to the non-root `oci` user via `su-exec` before `exec`-ing
`main.py`.
